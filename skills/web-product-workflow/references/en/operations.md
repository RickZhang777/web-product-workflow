<a id="benchmarks"></a>
## Competitor evidence

Select comparable products by target customer, core task, geography, and stage. Start with three to five candidates where available, then narrow the list based on evidence. Large platforms can illustrate a feature. Primary benchmarks should have comparable businesses and traffic patterns.

D records the target domain, reporting period, source, and metric definition. Review positioning, pricing, key features, search terms, SEO pages, and leading traffic sources. Cross-check with available tools. Verify which site a tool panel actually measures and report different periods or definitions separately. Mark missing data as unknown. QA checks each candidate's domain, period, sources, and comparability before accepting it as a formal benchmark.

<a id="pricing"></a>
## Plans and costs

PM defines customer value and entitlements, D estimates viability from usage and fulfillment costs, and ENG enforces entitlements on the server. Choose subscriptions, credits, or one-time charges according to frequency and cost. If using Free, Plus, and Pro, specify each plan's entitlements, when upgrades and downgrades take effect, and how limits change. A free trial should demonstrate the core value with per-user and site-wide cost boundaries.

When integrating payments, verify regional and business eligibility, fees, payout conditions, and refunds. Separate test payments, real receipts, and payouts. For payment and quota operations that may retry, verify idempotency and settle failures under the agreed rules. Before release, verify success, rejection, replay, and entitlement changes on the relevant version.

<a id="experiments"></a>
## Acquisition experiments

G chooses the channel with the highest concentration of target customers, then defines the landing page and desired action. Record the audience, channel, hypothesis, action, metric, total budget, observation window, and stop condition. Use the authorized cumulative budget for the project. With a small budget or sparse samples, run sequential tests and explain the limitations. Reallocate within the current authorization. The user decides on new spending.

<a id="metrics"></a>
## Metrics and review

D connects acquisition sources, visits, successful core tasks, first payments, renewals, refunds, and variable costs. Use existing analytics for acquisition, server-side events for business success and failure, and financial records for receipts and costs. Specify the time range, currency, source, and test status. Record off-site estimates separately from measurements of your own site.

Find the single bottleneck with the largest effect on customer value or contribution. Check completeness, sample size, and reporting delays before recommending the next test. Use reconcilable records for acquisition cost and contribution and state the denominator, expenses, and observation window. Keep missing and immature results visible.

<a id="portfolio"></a>
## Portfolio review

A shared portfolio analyst can read each site's data from D using consistent definitions. Daily reports list anomalies and actions. Weekly reports show successful use, payments, advertising and fulfillment costs, data gaps, and whether each site merits more investment, observation, repair, or a stop. Include evidence and a review date. The user decides and each site's O assigns the next work.
