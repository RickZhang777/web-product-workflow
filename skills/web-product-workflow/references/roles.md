# 岗位与交接

[English](en/roles.md) · **简体中文**

<a id="roles"></a>
## 六岗导航

| 岗位 | 本轮负责 |
|---|---|
| [O 统筹](#role-o) | 范围、优先级、权限、交接 |
| [PM 产品](#role-pm) | 客户、痛点、范围、产品结果 |
| [ENG 工程](#role-eng) | 复用模板、实现、自测和部署 |
| [QA 质检](#role-qa) | 独立验收、版本证据和复验 |
| [G 增长](#role-g) | 渠道、实验、授权内执行 |
| [D 数据](#role-d) | 竞品证据、测量口径、成本与复盘 |

<a id="role-o"></a>
## O 项目统筹

在现有任务记录确认本轮终点、优先级、唯一负责人、检查人及授权。可逆的假设写明后推进，花费和生产动作核授权。跨岗问题退对应责任人。通过条件是每个阻塞都有去向，每个阶段的证据能找到对应版本。QA 的验收和 D 的数据结论由各自签发。

<a id="role-pm"></a>
## PM 产品经理

交付可开工的产品说明。写清目标客户、使用场景、现有替代、具体痛点、第一项用户结果和首版范围。差异化可来自更细的场景、更高的成功率、更短的耗时或更低的成本。引用 D 的[竞品证据](operations.md#benchmarks)，区分观察到的事实和待验证的价值假设。每个首版功能都有验收条件和下一步验证。

<a id="role-eng"></a>
## ENG 全栈工程师

依据产品通过条件实现最小完整路径，明确已有、待适配与需新增能力。维护现有 SPEC 中受影响的关系。交付代码版本、运行方式、实现说明和自测结果。先按[工程与验收](engineering.md#changes)说明影响及检查范围，发布时走[发布门槛](engineering.md#release)。

<a id="role-qa"></a>
## QA 质量验收

作为独立检查人，依据原需求、代码变化和可访问的目标环境验证。用目标客户的任务复现成功、失败与恢复，核对本次变化关联的权限、数据、费用和可用性。交付[验收记录](engineering.md#qa)，把缺陷退 ENG 或把验收歧义退 PM。新版按实际影响复验。

<a id="role-g"></a>
## G 增长营销

按客群排渠道优先级，为首个渠道给出承诺、承接页、目标动作、预算和停止条件。基线和评估由 D 负责，产品承诺由 PM 核。交付[实验](operations.md#experiments)与执行回执，根据独立评估在已授权范围内调配。

<a id="role-d"></a>
## D 数据分析

维护一份可复核的[竞品底稿](operations.md#benchmarks)与[指标口径](operations.md#metrics)，由其他岗位引用。区分直接观测、第三方估算和未知。用相同口径定位最大短板，交付证据、影响、局限和一项优先验证建议。用户决定追加投入，O 安排对应岗位执行。

<a id="stages"></a>
## 七个阶段及其证据

| 阶段 | 主责 | 交付后才能判断的事 |
|---|---|---|
| 机会 | D | 对标规模、客户任务与数据证据是否可比 |
| 立项 | PM | 服务谁、核心结果、首版验收与范围是否明确 |
| 获客与测量准备 | G、D 各管各自产物 | 首个渠道、成功事件和预算是否有定义 |
| 实现 | ENG | 核心路径、异常路径及受影响功能能否验证 |
| 验收与上线 | QA 验收，ENG 部署，QA 复验 | 当前版本的证据、授权及目标环境状态是否对应 |
| 冷启动 | G | 实验行动、花费、承接页和目标动作是否可追 |
| 复盘 | D | 是否有足够样本支持继续、调整或停止，下一项交谁 |

接手旧项目或小改动时，按已核证据进入相关阶段。多站经营由共享的[组合分析](operations.md#portfolio)承担。

<a id="handoff"></a>
## 交接

在现有 PRD、SPEC 或任务记录中复用下列字段。

`唯一负责人｜范围与终点｜交付和通过条件｜检查人｜版本、证据及未测项｜下一接手人`

阻塞说明缺什么、谁能补、怎样验证。有独立证据的部分可先交付。检查命令、代码版本和实际结果对应后再更新状态。
